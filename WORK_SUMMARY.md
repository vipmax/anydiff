# Сводка выполненных работ: Оптимизация производительности, MultiBuffer и исправление багов

## 1. Оптимизация скорости открытия репозиториев (8 сек ➔ 0.4 сек)

### Проблема:
При открытии больших проектов (например, `bun` с 2 200+ изменёнными файлами) приложение зависало на **8+ секунд**.

### Причина:
Метод `loadDiff(files:)` в `MainWindowView.swift` синхронно считывал полный текст каждого из 2 232 файлов с диска через `String(contentsOfFile:)`.

### Решение:
1. **Ленивая инициализация**: убрано предварительное чтение всего диска. Буферы (`Buffer`) и срезы (`Excerpt`) создаются **напрямую из уже распарсенных строк диффа** в оперативной памяти.
2. **64KB SIMD Стриминг**: внедрены `GitStreamReader.swift` и `ChunkLineSplitter` в `GitDiffParser.swift` на базе векторной инструкции `memchr(0x0A)` без лишних строковых аллокаций.
3. **Результат бенчмарка**:
   * Время до первой отрисовки (TTFF) снизилось с **7.53 с** до **0.43 с** (**ускорение в 17.5 раз**).
   * Парсинг гигантского диффа на 1 029 583 строк: ускорение с **5.82 с** до **0.96 с** (**6.09x быстрее**).

## 2. Исправление бага слёта подсветки диффа при нажатии `Enter`

### Проблема:
При вводе новых строк (нажатии `Enter`) в добавленных блоках кода или новых файлах зелёная подсветка диффа (`.added`) сбрасывалась и все строки становились серыми (`.unchanged`).

### Причины:
1. **Перезапись `baselineLines` в конструкторе `Buffer`**:
   ```swift
   // Было:
   self.baselineLines = baselineLines.isEmpty ? lines : baselineLines
   ```
   Для новых файлов/ханков передавался пустой массив `baselineLines: []`, который тернарником перезаписывался текущими строками `lines`.
2. **Auto-Save сжигал Git Baseline**:
   При авто-сохранении по таймеру (200 мс) в `Buffer.saveToFile()` стояло `baselineLines = _lines`. Буфер забывал оригинальный Git HEAD и считал промежуточное состояние «базой».
3. **Фильтрация в `DisplayMap`**:
   В `DisplayMap.swift` условие пересчёта диффа требовало `!buffer.baselineLines.isEmpty`, из-за чего добавленные файлы пропускались и попадали в ветку сброса в `.unchanged`.

### Решение:
* `baselineLines` объявлен **неизменяемым Git-базисом**, который никогда не перезаписывается при сохранении.
* Конструкторы `Buffer` теперь строго сохраняют переданный `baselineLines: []`.
* `DisplayMap` корректно определяет `fileStatus == .added` и пересчитывает Myers LCS дифф на лету.

## 3. Защита от дублирования кода на диске (`lastSavedLineCount`)

### Проблема:
При серии быстрых правок с интервалом авто-сейва файл на диске повреждался и дублировал куски кода в конец файла (например, `GitDiffParser.swift` вырастал на тысячи строк).

### Причина:
Метод `saveToFile()` для частичных ханков брал для замены диапазон старой длины `baselineLines.count`. Если пользователь добавил строки, то при первом сейве они писались на диск, а при втором сейве заменялась только часть, оставляя хвост от предыдущего сохранения.

### Решение:
* Введено поле `lastSavedLineCount` в `Buffer`, которое отслеживает реальное количество строк, занятых буфером на диске после последнего сохранения.
* При повторных авто-сохранениях замещается ровно диапазон `replaceStart..<(replaceStart + lastSavedLineCount)`.

## 4. Синхронизация смещений в файлах с несколькими ханками (Multi-Hunk)

### Проблема:
Если в одном файле открыто несколько ханков (например, на строках 10 и 50), добавление строк в первый ханк смещало файл на диске, но второй ханк в памяти сохранял старый `startLineNumber = 50`, из-за чего второй ханк перезаписывал чужие строки.

### Решение:
1. **Динамический сдвиг оффсетов**: при любых вставках/удалениях в `MultiBuffer.replace` и `CustomMultiBufferEditorView.updateExcerptsAfterEdit` все последующие буферы того же файла автоматически сдвигают свой `startLineNumber` на дельту строк.
2. **Reverse Splicing**: при общем сохранении `saveAllDirtyBuffers` буферы одного файла сортируются снизу вверх (`startLineNumber >`), чтобы правки в верхних ханках не ломали оффсеты нижних.

## 5. Слияние смежных ханков при раскрытии контекста (Duplicate Lines Bug)

### Проблема:
При нажатии на стрелки раскрытия контекста ($\uparrow$ / $\downarrow$) между двумя соседними ханками одного файла возникали дублирующиеся строки с двойными стрелками.

### Решение:
* В `MultiBuffer.mergeAdjacentExcerpts` реализовано склеивание перекрывающихся/соприкасающихся срезов даже если они изначально принадлежали разным `BufferId`.
* Добавлен метод `Buffer.mergeFrom(buffer:overlap:)`.
